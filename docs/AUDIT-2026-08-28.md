# Kernel governance audit — 2026-08-28

This is evidence, not an eighth operating document. The seven operating files
remain `README.md`, `AGENTS.md`, `docs/KERNEL-CONTRACT.md`,
`docs/ENFORCEMENT-REGISTER.md`, `docs/OPERATIONS.md`, `docs/DEGRADED-MODE.md`,
and `CHANGELOG.md`. `tests/test_surface.py` excludes `docs/AUDIT-*.md` from that
set so an in-tree audit can exist without amending the kernel contract.

No kernel runtime behavior is changed by this file.

## 1. Scope and method

Audited repository: `gillella/Aru_Agentic_SDLC` at
`311ed91` (merge of PR 521, 2026-08-28). Compared the seven canonical documents
plus skills, hooks, scripts, tests, the `aru-protect-main` ruleset, live GitHub
metadata, and `gillella/aru-golden-path-demo`.

Method:

1. Read the seven operating documents and the enforcement register.
2. Read the scripts, hooks, skills, and tests against that contract.
3. Ran the test suite and ruff.
4. Queried GitHub for open issues/PRs, labels, leftover branches, releases, and
   the main-branch ruleset.
5. Reproduced parser drift between `common.py` and `hooks/enforce_touches.py`.
6. Inspected the public golden-path demo.

Prompt context that survived verification is marked as verified. Prompt context
that did not is listed in §8.

## 2. Intended contract (what the kernel claims)

Aru is a fail-closed rules kernel: one approved GitHub issue → exclusive claim
and `touches:` paths → worktree → PR → exact-head CI → one distinct
authoritative reviewer → merge only via `scripts/merge_pr.py`.

Mechanical authorities, per `docs/ENFORCEMENT-REGISTER.md`:

| Control | Mechanism |
| --- | --- |
| issue contract | `triage_backlog.py` |
| five statuses | `update_issue_status.py` |
| exclusive claim | `claim_issue.py` |
| path budget | `hooks/enforce_touches.py` |
| default-branch push | `hooks/pre-push` |
| worktree isolation | `create_branch.py` |
| closure link | `create_pr.py` |
| reviewer + 15-minute fallback | `create_pr.py` |
| exact-head CI / review / merge | `check_ci.py`, `fetch_pr_feedback.py`, `merge_pr.py` |

Anything not in that table is guidance. That distinction matters: several
promises in `AGENTS.md` and `README.md` are guidance wearing authority language.

Surface at HEAD: 3,360 production Python+hook lines (budget 6,000); 3,308 test
lines (budget 9,000); 14 command scripts (budget 12–14, at the cap); 6 skills
(at the cap); `scripts/create_pr.py` is 784 lines (file cap 800, preferred 400).

## 4. Approach judgment

The philosophy is coherent: keep one visible ledger (GitHub), refuse a second
database, fail closed on missing evidence, and keep the kernel small. Several
mechanical pieces actually do that — `--expected-head` plus `--match-head-commit`,
GraphQL authority splitting, coding-review SHA binding, claim-race rollback, and
the refusal to invent degraded-mode state.

The approach still has structural limits that code polish cannot remove:

1. **GitHub is a leaky control plane.** Labels, Project items, the PR merge
   button, and local Git hooks are independently writable. A kernel that names
   `merge_pr.py` as the only merge authority cannot enforce that unless GitHub
   itself refuses every other path. Today it does not (§5.H1).
2. **Labels are the real state machine; the Project Board is a write-through
   display.** `status_of()` never reads Project V2. The docs say the board is
   lifecycle authority. The code treats `status:*` labels as authority and
   updates the board as a side effect. Two stores, one of them decorative.
3. **No scheduler is a product choice with a visible cost.** Fallback, claim
   recovery, and stalled PRs require a human or agent to come back and type a
   command. `gillella/aru-golden-path-demo` has been sitting In Review since
   2026-08-18. That is the design working as specified, and it is why a
   "complete" kernel can still leave work unfinished.
4. **The reviewer state machine is the complexity hotspot of an allegedly
   minimal kernel.** Initial assignment, 15-minute pending, explicit
   unavailability, coding probes, four families, Claude subscriptions, binding
   labels, attestation JSON, CodeAnt markers, and no-op SUCCESS detection live
   in ~1,500 lines across `create_pr.py` and `merge_pr.py`. This is also where
   docs and tests currently disagree (§5.H2).
5. **The freeze did not freeze review policy.** `CHANGELOG.md` and `README.md`
   still say v0.2.2. Tags `v0.2.3` and `v0.2.4` exist. HEAD is past `v0.2.4`
   (PRs 519 and 521) with no changelog. Correctness patches are allowed during
   the freeze; silent version identity is not a correctness property.
6. **Adoption cost is larger than the kernel.** A consumer needs Python 3.11+,
   `gh`, one Project V2 with five exact statuses, split PAT/App auth for
   Projects, `reviewer-registered:*` and/or `ARU_CODING_REVIEWERS` plus
   bindings, hooks, `ARU_SDLC_HOME`, and a real CI workflow. Bootstrap writes
   `python3 -m compileall` as CI and does not create a ruleset or register a
   reviewer. The kernel is small; the prerequisites are not.
7. **`touches:` is enforced at the wrong layer.** The write boundary is a local
   pre-push hook. Merge does not re-read the PR diff. `--no-verify`, a missing
   hook install, the GitHub web editor, and any App push bypass it.

Recommendation: keep the no-scheduler identity. Stop claiming fail-closed for
controls that GitHub will not enforce. Move the write boundary and the merge
gate onto server-side evidence. Make labels *or* the board the lifecycle
authority, not both. Simplify or honestly document the reviewer machine as
external-first. Restore version/changelog discipline even during the freeze.

## 5. Ranked findings

Severity:

- **Blocker** — the documented fail-closed claim is false for a path an operator
  can take today without exploiting a bug.
- **High** — real bug, fail-open gap, or contract/code contradiction that can
  admit the wrong merge, wrong reviewer, or wrong write set.
- **Medium** — operational footgun, untested critical path, or stale docs that
  will mis-train agents.
- **Low** — hygiene, budget pressure, leftover inventory.

Hypotheses are labeled.

### Blocker

#### B1. `merge_pr.py` is not the only merge authority

**Evidence.** Repository ruleset `aru-protect-main` (id `20802441`, active,
`current_user_can_bypass: never`) requires:

- status check `Lint, Verify & Test` with `strict_required_status_checks_policy`
- unresolved review-thread resolution
- no branch deletion / non-fast-forward

It also sets `required_approving_review_count: 0`,
`dismiss_stale_reviews_on_push: false`, and
`allowed_merge_methods: ["merge","squash","rebase"]`.

`scripts/merge_pr.py` merges with `gh pr merge --merge --match-head-commit`.
Anyone with write access can still merge from the GitHub UI once CI is green
and threads are resolved, including squash and rebase, without exact-head
review, without `--expected-head`, and without marking the issue Done through
`close_out()`.

`docs/ENFORCEMENT-REGISTER.md` lists `scripts/merge_pr.py` as merge authority.
`AGENTS.md` says the same. The ruleset is the actual merge authority, and it is
weaker.

This is an approach limit, not a missed `if`. GitHub cannot require "was merged
by this Python script" unless a required check or GitHub App is the only
allowed merger.

### High

#### H1. Issue-form `### touches:` is accepted by triage and refused by the push hook

**Evidence, reproduced 2026-08-28.** `common.parse_touches()` accepts rendered
issue-form markdown (`tests/test_common.py::test_issue_contract_accepts_rendered_issue_form_markdown`).
`hooks/enforce_touches.py:parse_touches` only matches an inline
`touches: …` line. Against the form body used in that test:

```text
common.parse_touches: ['scripts/a.py', 'docs/**']
hook.parse_touches RAISED: Refusal issue must contain exactly one touches: declaration
```

`.github/ISSUE_TEMPLATE/governed-task.yml` labels the path field `"touches:"`,
so GitHub renders `### touches:`. `docs/OPERATIONS.md` §9 documents that form
as a valid Ready contract. An issue filed from the template can be triaged and
claimed, then every push fails the hook.

`create-github-issue/SKILL.md` still tells agents to write the inline form, so
skill-created issues happen to work. Template-created issues do not.

#### H2. Documented reviewer rotation is not what the code does

**Evidence.** `tests/test_reviewer_distribution.py::test_initial_assignment_strictly_prefers_external_reviewers`
asserts that with CodeRabbit and Sourcery both registered, issues 0–3 all get
`coderabbit`. `choose_initial_reviewer()` in `scripts/create_pr.py` returns the
first registered external and never consults the issue number unless every
external is unregistered.

This repo has `reviewer-registered:coderabbit`, `sourcery`, and `codeant`.
Initial authority is therefore always CodeRabbit.

`README.md`, `AGENTS.md`, `docs/KERNEL-CONTRACT.md`, `docs/OPERATIONS.md` §4,
and `skills/implement-next-issue/SKILL.md` still describe one pool of externals
plus coding identities with issue-number rotation of the starting slot. That
text matches GitHub release `v0.2.4` and PR 516. PR 519 (`7bb9ec3`, "enforce
external-first coding fallback") changed the machine; the operating docs were
not brought along.

Agents that follow `AGENTS.md` will expect distribution they will not get.

#### H3. `touches:` is not a merge gate

**Evidence.** `scripts/merge_pr.py` never calls `parse_touches` or
`path_allowed`. `create_pr.py` never diffs the branch against the issue budget.
The only mechanism in the enforcement register is `hooks/enforce_touches.py`,
invoked from `hooks/pre-push`.

Bypass paths that need no bug:

- `git push --no-verify`
- a clone without `install_hooks.sh`
- GitHub web UI / codespace without the hook
- a GitHub App or `ARU_GITHUB_APP_RUNNER` push that does not run local hooks

`docs/OPERATIONS.md` already admits local hooks are not a server-side boundary
for default-branch pushes. It does not admit the same for the write budget.

#### H4. Lifecycle authority is labels, not the Project Board

**Evidence.** Every helper that decides Ready / In Progress / In Review / Done
calls `status_of()`, which reads `status:*` labels only
(`scripts/common.py`). `set_status()` writes the label first, then the board,
and no-ops when the label already matches — so a board card that drifted is
never repaired. `update_issue_status.py` is a raw setter: any of the five
statuses, no legal-transition table, no contract check. It is a supported
command in the kernel contract.

If an operator (or the GitHub Project UI, or a Project workflow) moves a card
without changing labels, Aru ignores the board. If someone runs
`update_issue_status.py --status Done` on a Ready issue, the kernel will do it.

The docs' "do not create another lifecycle store" is already violated in
spirit: labels and Project V2 are two stores that can diverge.

#### H5. Claim release does not require In Progress

**Evidence.** `claim_issue.release()` checks exclusive claimant identity, then
unassigns and `set_status(..., "Ready")`. It does not require current status
`In Progress`. An In Review issue with an open PR can be returned to Ready and
re-claimed by another agent. Untested: `tests/test_issue_flow.py` covers claim
settle and claim-race rollback, not release.

#### H6. External no-op SUCCESS can satisfy the merge gate when the Statuses API is empty

**Evidence.** `successful_service_check()` in `scripts/merge_pr.py` returns
`True` when the rollup check is success and `review_statuses(head)` is empty.
CodeRabbit and most GitHub Apps report through the Checks API, not
`/commits/{sha}/statuses`. The rate-limit test
(`test_rate_limited_success_status_does_not_satisfy_coderabbit`) only covers
the path where a commit status *with* `description: "Review rate limited"`
exists.

`create_pr.external_state()` is stricter when that status is present, so
fallback and merge can disagree: fallback may retain "available" from a
description-less rollup SUCCESS, and merge will accept it.

**Hypothesis:** production CodeRabbit no-op / quota messages live in check-run
output or a comment body, not in commit statuses. If so, a nominally successful
no-op review satisfies `merge_pr.py` today. The docs claim the opposite
(`README.md` reviewer state machine; `AGENTS.md` "cannot satisfy the merge gate
through a nominally successful no-op status").

#### H7. Published version identity is false

**Evidence.**

| Source | Identity |
| --- | --- |
| `README.md` / `CHANGELOG.md` | Complete v0.2.2 (2026-08-27) |
| Git tags | `v0.2.0` … `v0.2.4` |
| GitHub releases | v0.2.3 "Governed Reviewer Fallback"; v0.2.4 "Distributed Review and Coordination Efficiency" |
| `HEAD` | `311ed91`, after `v0.2.4`, including PR 519 (external-first) and PR 521 (deleted-path touches) |

`v0.2.4` points at `2861cbe` (PR 517, GraphQL quota). PRs 519 and 521 have no
release and no changelog. The freeze allows correctness fixes; it does not
allow the canonical version line to name a tag that is two releases and two
merges behind HEAD.

### Medium

#### M1. Leftover issue branches were not removed

**Verified.** `git branch -r | grep issue-` returns 31 remotes, including
pre-reset names (`feat/issue-259-featreaper-…`, `fix/issue-355-fixslack-…`,
`fix/issue-342-fixvisualizer-…`) and recently merged ones
(`origin/fix/issue-518-…`, `origin/fix/issue-520-…`). Open issues: 0. Open PRs:
0. `CHANGELOG.md` v0.2.2 claims legacy heads were archived and obsolete
branches removed. `cleanup_worktrees.py` deletes local Factory worktrees only,
and only `feat|fix|docs` / `codex/` branch names — not remotes, not `chore/`.

`merge_pr.py` passes `--delete-branch`; leftover `origin/fix/issue-520-*`
means that merge did not delete the ref, or the branch was re-pushed, or the
merge was not performed by `merge_pr.py`.

#### M2. Label inventory is unbounded

**Verified.** 382 labels. `ensure_label(..., --force)` creates `agent:*`,
`author:*`, `reviewer:*`, `reviewer-actor:*` on demand and never deletes them.
Leftovers include `reviewer-actor:gillella`, `review:agent`, dozens of
`agent:` / `author:` / `merger:` identities from the pre-reset factory, and
all twelve current bindings.

`registered_external_states()` / `registered_coding_actors()` use
`gh label list --limit 1000`. 382 < 1000 today. The test
`test_external_registration_reads_beyond_first_hundred_labels` only proves the
limit is 1000, not that truncation fails closed.

#### M3. Golden-path demo is stalled on a pre-reset contract

**Verified.** `gillella/aru-golden-path-demo` is public. Description still says
"idea → Ready → PR → review → merge → **preview**". Issue #2 is OPEN,
`status:in-review`, `agent:cursor-1`, last updated 2026-08-18, with
`build_preview.py` in its acceptance criteria. PR #3 is OPEN with labels
`author:cursor-1`, `family:xai`, `needs-review` — not `author-family:*` /
`review:<authority>`. That is not a completed v0.2.2 golden path. It is
evidence that without a scheduler, a demo walk stops when the operator does.

#### M4. `fetch_next_work.py` freezes on the first authored PR

**Evidence.** `select()` iterates authored PRs and `return`s wait/feedback/ci
on the first one. A waiting review on PR A prevents picking up PR B's red CI
or a new Ready issue. Intentional (one unit of work, no scheduler) and an
operational stall mode. Untested for "second PR exists".

#### M5. Triage inventory is capped at 200; picker is not

**Evidence.** `common.list_issues()` uses `gh issue list --limit 200`.
`triage_backlog.py` uses that helper. `fetch_next_work.ready_issues()` uses
`gh_paginated`. A 201st Backlog issue is invisible to triage and can still be
claimed if someone already moved its label. Fail-closed would refuse a
truncated inventory.

#### M6. CI treats `NEUTRAL` as success and does not bind checks to the head SHA

**Evidence.** `check_ci.check_state()` maps `SUCCESS` and `NEUTRAL` to
`success`. GitHub path-filtered / skipped checks conclude `neutral`. A PR whose
only non-review checks are NEUTRAL is mergeable through `merge_pr.py` if the
rollup is otherwise empty-of-failures.

`ci_verdict()` trusts `gh pr view --json statusCheckRollup` for the current
PR without checking each record's SHA. GitHub Actions `pull_request` checkout
in `.github/workflows/ci.yml` and `templates/ci.yml` uses the default merge
commit, not `ref: ${{ github.event.pull_request.head.sha }}`. The kernel's
"exact-head CI" is GitHub's attribution of a merge-commit run onto the head
SHA. Usually close enough; not the same as testing the head tree.

Consumer template CI is `python3 -m compileall -q .`. Adopting that workflow as
the required check (`Lint, Verify & Test` is this repo's name; the template job
is also `verify`) gives a green merge gate that compiles Python and does
nothing else.

#### M7. Fifteen-minute window depends on the issue Events API

**Evidence.** `_authority_assigned_at()` reads
`/repos/{slug}/issues/{number}/events?per_page=100` via `gh_paginated`. GitHub
caps issue events; a busy PR can lose older `labeled` events. Missing
assignment events fall back to `pr.createdAt`, which can either delay fallback
(clock starts too early — actually that would *shorten* the wait if createdAt
is earlier) or, after many label flips, miss the latest assignment and reuse
an older timestamp.

**Hypothesis:** on a PR with >300 issue events, the pending window can fire
immediately or never, depending on which `labeled` events remain. No test
injects a truncated event list.

#### M8. Degraded mode is a document, not a mechanism

**Evidence.** `docs/DEGRADED-MODE.md` tells humans to stop. `scripts/` contain
no rate-limit, 403, or backoff handling (`rg` over `scripts/` for
`rate.?limit|backoff|X-RateLimit` is empty). GraphQL quota exhaustion fails
the current command with `KernelError`. That is fail-closed per invocation and
does not prevent a loop of agents from retrying until the hour resets. PR 517
narrowed board GraphQL; it did not add a quota brake.

#### M9. `update_issue_status.py` and bootstrap leave the dangerous work to operators

Bootstrap (`init_project.py --github`) creates the repo, status/type/priority
/review labels, and a Project with five Status options. It does not: commit,
push, create a ruleset, add `reviewer-registered:*`, create bindings, install
CodeRabbit, or replace `compileall` CI. `templates/AGENTS.md` is a short
summary that still says "Prefer CodeRabbit, then Sourcery, then CodeAnt" —
aligned with code, not with the rotation paragraphs in the kernel `AGENTS.md`.

`KERNEL-CONTRACT.md` still names "Hermes or a human" as who schedules work.
Hermes is outside this repository; leftover language from the pre-reset
factory. `install_agent_integration.sh` symlinks skills into
`~/.agents`, `~/.codex`, and `~/.cursor` only — not Claude or Antigravity —
while those families are first-class coding reviewers.

#### M10. Coding attestation is self-asserted; bindings are ordinary labels

**Evidence.** Authoritative coding review is a GitHub Review whose body contains
`<!-- aru-coding-review:v1 {json} -->` with required keys, a 40-character SHA,
and `submitted_by` matching a `reviewer-actor:*` label. Merge correctly rejects
self-review when the GitHub actor equals the PR author, stale SHAs, generic
summaries, and `REQUEST_CHANGES`.

Anyone who can apply labels can retarget `reviewer-actor:` and
`reviewer-binding:`. Anyone who can submit a Review as that actor can mint a
valid attestation. The JSON does not prove the diff was read; it proves a
distinct GitHub identity was willing to post a structured comment. That may be
the strongest primitive GitHub offers. It should be described as such, not as
anti-spoofing in the cryptographic sense. `AGENTS.md` says "malformed/spoofed
/conflicting evidence" blocks merge; spoofing here means "wrong actor / wrong
SHA / duplicate marker", which the code does check.

#### M11. Duplicate coding-probe implementations can drift

**Evidence.** `common.probe_coding_candidate()` and
`create_pr.probe_coding_reviewer()` both know Claude `claude-sub`, Codex
`codex exec --skip-git-repo-check`, Cursor `cursor-agent -p`, Antigravity
`agy -p`, and the `OK` stdout rule. Fallback/assignment uses `create_pr`'s
copy (family preference, Claude rotation). A later edit to one path will not
fail a test on the other.

#### M12. File-size and command-count pressure sits on the reviewer machine

`create_pr.py` 784, `common.py` 736, `merge_pr.py` 681, against a preferred 400
and a hard 800. Command scripts are at 14/14. A merge-time `touches:` check
must land inside `merge_pr.py`, not as a 15th command. Adding reviewer
providers, a quota brake, or a ruleset helper requires deleting something or
breaking the budget tests.

### Low

#### L1. Seven-document budget cannot record an audit without a test exception

This file exists only because `test_active_documents_are_exactly_the_kernel_set`
was taught to ignore `docs/AUDIT-*.md`. That is the budget working, and it is
why operating docs stay stale (there is nowhere to put a long investigation
without violating the contract).

#### L2. Leftover `reviewer-actor:gillella` label

Present on the kernel repo. Bindings currently point at
`aru-code-factory-gillella[bot]`. The leftover name can still be applied by
hand. Merge would then require a Review from `gillella`, which is also the
typical PR author — self-review would fail. Footgun, currently fail-closed at
merge if someone uses it on a `gillella`-authored PR.

#### L3. Outdated threads are dropped

`fetch_pr_feedback.py` skips `isOutdated` threads. Combined with exact-head
review this is usually right. A finding that became outdated after a push and
was never re-stated on the new head will not block merge. External providers
are expected to re-review the new head; if they do not, H6/M6 apply.

#### L4. `depends-on:` without `#N` is silent

`common.dependencies()` only matches `depends-on: #123`. The golden-path issue
body contains a bare `depends-on:` line. Contract validation ignores it.

#### L5. Pre-push default-branch protection is local only

Already documented. Restated because the ruleset *does* exist here, but
consumer bootstrap does not install one.

## 7. Proposed roadmap

### Leave alone (the product)

- No scheduler, daemon, capacity ledger, Slack bridge, dashboard, preview, or
  `aru code` loop. The stalled golden-path demo is an argument for a human
  operator, not for rebuilding the pre-v0.2 factory.
- Six skills, ≤14 commands, no tracked runtime JSON/SQLite.
- `--expected-head` / `--match-head-commit` recheck.
- Distinct GitHub actor for coding review; SHA-bound attestation schema.
- GraphQL repository vs Project authority split and token redaction.
- Fail closed when `ARU_CODING_REVIEWERS` is missing while bindings exist.
- Feature freeze through 2026-09-26 for *features*. Correctness below is
  freeze-compatible.

### Change (correctness, allowed now)

Priority order is the merge-safety order.

1. **Make `touches:` one parser.** `hooks/enforce_touches.py` should import or
   copy `common.parse_touches` / `path_allowed` so issue-form and inline
   declarations cannot diverge. Add the rendered-form case to
   `tests/test_enforce_touches.py`. This is H1 and is a hook bug, not a
   feature.
2. **Re-check the write budget at PR create and merge.** `create_pr.py` and
   `merge_pr.py` should refuse unless every path in
   `git diff --name-only base...head` (including deletes, as PR 521 already
   requires in the hook) is allowed by the linked issue's `touches:`. Client
   hooks stay as a fast local signal; they stop being the authority.
3. **Close the GitHub UI merge hole, as far as GitHub allows.** On this repo
   and in bootstrap docs: `allowed_merge_methods: ["merge"]`,
   `dismiss_stale_reviews_on_push: true`, and a required check that only
   `merge_pr.py` posts (or restrict merging to a GitHub App whose token is
   what `merge_pr.py` uses). Zero approving reviews is acceptable only if the
   Aru gate *is* that required check. Document honestly that without this,
   `merge_pr.py` is a convention.
4. **`release()` must require `In Progress` and no open PR for that issue.**
   Fail closed otherwise.
5. **`update_issue_status.py` needs a legal-transition table** (the OPERATIONS
   state diagram already draws it) or should be demoted out of the supported
   command list. A raw setter is not an enforcement mechanism.
6. **No-op SUCCESS must fail closed without Statuses API data.** Read check-run
   output / text, or treat "rollup SUCCESS + empty statuses + no trusted
   APPROVED review" as pending, not mergeable. Align `external_state()` and
   `successful_service_check()`.
7. **Stop treating `NEUTRAL` as CI success.** Pending or failure; not success.
8. **Fix the docs to match PR 519**, or restore PR 516 rotation and change the
   tests. Do not leave `AGENTS.md` describing a pool the code will never
   consult. External-first is the simpler machine; rotation-across-coding was
   the v0.2.4 story. Pick one.
9. **Publish a truthful version.** Either tag `v0.2.5` with PRs 519/521 and
   write `CHANGELOG.md`, or stop labeling HEAD as v0.2.2. The freeze is not a
   reason to freeze the changelog.

Smaller correctness: fail closed when `gh issue list --limit 200` is full;
require `origin/main` in `create_branch.py` rather than silently using local
`main`; check issue-event pagination completeness for the 15-minute clock.

### Add (after freeze, or as operator work that is not kernel code)

- **Server-side merge check** as in item 3, shipped as a workflow the consumer
  can copy. Not a 15th Python command if a GitHub Actions job can do it.
- **Remote-branch archive pass** for the 31 leftover `issue-*` refs. This is
