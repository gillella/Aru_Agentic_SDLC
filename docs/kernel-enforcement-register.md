# Kernel Enforcement Register

This register is the canonical inventory of shipped controls that can permit,
block, or authorize an Aru lifecycle transition. It separates the mechanisms
that may be trusted by the software-factory kernel from useful but bypassable
advice. The classification is about authority, not code quality.

## Authority classes

**Authoritative** controls are part of the current trusted computing base
(TCB). A positive result may authorize the transition named in the register.
Unknown, missing, stale, malformed, or partially read authority input fails
closed: the transition does not proceed. If an irreversible server mutation
has already happened, later failure makes close-out incomplete; it never
rewrites the successful mutation as though it did not occur.

**Advisory** controls improve safety, attribution, or visibility but cannot
authorize a transition and cannot be the sole reason one is blocked. They may
fail open compliantly only under the evidence contract below. A control that
does not meet it remains an explicitly noncompliant advisory gap; its output
cannot be used as lifecycle evidence. An advisory control that is absent,
deliberately bypassed, or noncompliant is outside the TCB.

### Advisory fail-open evidence contract

A compliant fail-open decision MUST emit one JSON line with schema
`aru.advisory.v1` and fields `control_id`, `outcome`, `reason`, and `timestamp`.
`control_id` is the stable ID in this register and `outcome` is
`allowed_without_check`. The caller MUST persist that exact event in a durable
run or session audit and retain a locator that can be recorded on the governed
issue or PR. Prose, an exit code, console output, or an unretained stderr line
does not substitute for the JSON event plus durable sink.

Every fail-open row's Audit evidence cell therefore starts with either
`COMPLIANT aru.advisory.v1 durable sink:` and names the sink and locator, or
`NONCOMPLIANT:` and names the missing schema or retention boundary. A
noncompliant row remains useful as advice, but its fail-open result is an
evidence gap and cannot enter the TCB.

Authority belongs to the complete invocation named below, not merely to a file.
For example, governed board mutation means `update_issue_status.py
--require-board`, exact-head merge means `merge_pr.py --expected-head <SHA>`,
and hosted CI protection means the GitHub ruleset plus its required workflow.
Compatibility modes and read-only wrappers do not inherit that authority.

The register is organized by enforcement point rather than by source file.
Implementation-only components inherit the row of the authority that calls
them: `scripts/build_preview.py` and `scripts/smoke_preview.py` belong to
`ARU-PREVIEW-DEPLOYMENT`; CI's documentation, line-ceiling, import, dependency,
secret, lint, syntax, and test checks belong to `ARU-CI-PROTECTION`; and the
fleet runner composes dispatch, status, and loop-control rows. Installers,
doctors, metrics, visualizers, and pruning reports do not authorize lifecycle
transitions. Prompt-only skills also do not enter the TCB merely by stating a
rule. If any such component gains an independent allow, block, mutation, or
authorization decision, it needs a stable ID in this table in the same change.

## Composition and evidence rules

1. A lifecycle transition is authorized only by the authoritative row or rows
   that protect it. Advisory output can add context but cannot replace a
   missing authoritative verdict.
2. GitHub is the canonical cross-agent coordinator. Local registries are
   secured materializations for runtime presence, project routing, stop state,
   and Delivery Increments; none may become a fallback work queue.
3. `scripts/check_ci.py`, `scripts/fleet_status.py`, local hooks, agent presence,
   and Slack notifications are observers or early warnings. A green or quiet
   observer result is not permission to merge, promote, or close work.
4. The promotion workflow records audit-only GitHub Environment and Deployment
   state. It does not prove that a runnable build moved between real hosting
   environments. Preview deployment is a separate row because it produces a
   concrete artifact or library-skip record, URL when applicable, and smoke
   evidence.
5. An authoritative helper that has already committed an irreversible server
   mutation must preserve that truth. Merge close-out failure therefore means
   "merged, close-out incomplete", never "not merged".
6. `ARU-PR-ADMISSION` records at least one focused verification command bound
   to the current head; it is evidence admission, not a completeness verdict.
   `ARU-ACCEPTANCE-EXECUTION` and `ARU-DOD` enforce the issue-declared
   predicates before merge. The complete supported suite runs at each roadmap
   phase exit under #341 and again at the framework release gate under #357.

## Phase 1 kernel ADR consumption contract

The Phase 1 kernel architecture decision record MUST cite
`docs/kernel-enforcement-register.md` as a normative input and list the stable
IDs it places inside the kernel TCB. It may select only rows classified
**Authoritative**. An unregistered mechanism MUST NOT be described as part of
the TCB, a merge authority, an admission authority, or a lifecycle state
authority.

Adding or changing an enforcement point requires the same change set to update
this register and `tests/test_kernel_enforcement_register.py`. Promoting an
advisory mechanism requires a concrete fail-closed implementation and durable
evidence path before its class changes. The future capability-admission
validator and mandatory governance hooks or gates are kernel controls, not
optional capability packs; each must receive an authoritative stable ID before
the ADR can trust it. Optional plugins, connectors, skills, and subagent
adapters remain outside the TCB unless an authoritative registered admission
control evaluates them.
